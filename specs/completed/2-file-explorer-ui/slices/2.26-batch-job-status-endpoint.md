# Slice 2.26: Batch job status endpoint

## Status and outcome

**Completed September 13, 2026. Parent: main spec 2. Depends on 2.14.** Added one authenticated read-only
endpoint so the explorer can refresh loaded processing items without refetching
or replacing paginated folder contents.

## Work

- Add `GET /api/jobs/statuses?ids=<comma-separated IDs>`.
- Accept one `ids` parameter containing 1–100 unique positive base-10 job IDs.
  A missing parameter, empty/malformed/duplicate member, zero/negative ID, extra
  `ids` parameter, or larger set returns `400 invalid_job_ids` with field `ids`.
- Query all accepted IDs in one store call. Return `{jobs: [...]}` in request-ID
  order with `jobId`, `clipId`, clip `state`, measured `progress` when known,
  safe `errorMessage` when applicable, and `sizeBytes` when known. Nullable
  values remain JSON `null`; do not fabricate progress, errors, or size.
- Normal users may see only their own jobs. Administrators retain the existing
  acting-user context rules. Omit missing and unauthorized IDs identically; do
  not reveal which condition occurred and do not fail the rest of the batch.
- Reuse existing job/clip state definitions and authorization helpers. Do not
  expose source paths, internal processor details, storage keys, or stack text.

## Verification

Store and HTTP table tests cover 1 and 100 IDs, request ordering, mixed states,
nullable fields, all invalid-input classes, normal-user ownership, administrator
acting context, mixed allowed/omitted IDs, indistinguishable missing/unauthorized
omission, one store query per request, stable JSON names, and no metadata leak.
