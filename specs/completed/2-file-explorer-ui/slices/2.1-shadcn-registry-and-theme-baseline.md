# Slice 2.1: shadcn registry and theme baseline

## Status and outcome

**Completed September 12, 2026. Parent: main spec 2.** A reproducible
Radix-backed shadcn baseline is in place without changing application behavior.

## Work

- Keep `web/components.json` on the Radix provider and existing aliases.
- Use shadcn CLI `4.21.0` exactly. Add a short registry manifest
  beside `components.json` listing CLI version, component names, source style,
  and review date.
- Adopt the CLI's generated `cn` package imports. Keep `@/lib/utils` as a narrow
  compatibility re-export during migration; remove `clsx` and
  `tailwind-merge` only when `rg` proves no remaining direct consumer.
- Pin every newly introduced direct dependency in `web/package.json` and update
  `web/package-lock.json`; do not loosen unrelated versions.
- Map charcoal, slate, sky, success, warning, and destructive colors plus shared
  radius/focus-ring values into `web/src/index.css` tokens.
- Preserve semantic Button variants needed by accepted workflows, but align
  Button/Card/Input APIs with upstream composition before consumers migrate.

## Boundaries and verification

No screen, API, focus, or keyboard behavior changes. Build/lint passes, existing
component tests pass, the manifest matches installed source, and a token-level
contrast check covers normal, muted, focus, success, warning, and destructive
text.

## Implementation evidence

- `cn` `0.3.0` is pinned; registry components import it directly and
  `@/lib/utils` re-exports it for compatibility. Direct `clsx` and
  `tailwind-merge` dependencies were removed after the source audit.
- `web/shadcn-registry.json` records shadcn CLI `4.21.0`, Radix, New York style,
  and the installed baseline components.
- Semantic dark-theme tokens and automated WCAG AA token checks cover the
  accepted palette while preserving existing rendered utility classes.
- Frontend lint, 13 unit tests, production build, Docker web image build, API
  readiness, and live web HTTP 200 verification passed on September 12, 2026.
- The web development entrypoint fingerprints `package-lock.json` and runs
  `npm ci` only when the persistent Compose `node_modules` volume is stale, so
  newly pinned registry dependencies are available after an ordinary rebuild.
