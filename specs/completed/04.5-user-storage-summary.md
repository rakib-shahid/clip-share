# Administrator user-storage summary

## Status

**Completed 2026-09-06.** This read-only administrator convenience
feature. It does not create quotas, change stored-file limits, retain additional
media, or alter any upload, trash, restore, or public-link behavior.

## Objective

When an administrator opens **Manage users**, each user card shows the amount
of finalized media currently occupying server storage for that user. The compact
summary reads in this form:

```text
50 MB per stored clip · User · 1.38 GB used
```

The administrator card follows the same format, using `Super-admin` in place of
`User`.

## Storage accounting contract

- `storedBytes` is the sum of `clips.size_bytes` for every clip owned by the
  user with `state = 'ready'`.
- It includes ready clips in the recycle bin and in an archived library because
  their final media still occupies disk space until a permanent purge succeeds.
- It excludes queued, validating, processing, failed, and cancelled clips:
  reservations and temporary sources are not finalized stored media and do not
  have a reliable final byte count.
- A user with no ready media receives `storedBytes: 0` and displays `0 B used`.
- The number is an informational snapshot, not a quota and not a percentage of
  the per-clip stored-file limit. The existing per-clip limit remains unchanged.
- Totals are derived from SQLite at read time. Do not add a mutable counter,
  cache, background aggregation job, or schema migration for this feature.

## API and persistence

- Extend the existing administrator-only `GET /api/users` response so each user
  object includes `storedBytes` as a JSON integer. Do not create a second
  endpoint or expose this field to a normal user.
- `internal/store` owns one aggregate query or a query joined into the existing
  user list. It must use `COALESCE(SUM(...), 0)` and avoid an N+1 query per user.
- The query is ownership-based rather than folder-path based, so folder moves,
  user renames, readable media relocation, trash, and restore require no special
  accounting logic.
- Existing API fields and their meanings remain unchanged. Admin user mutations
  may return the existing user shape without a total; the modal refresh is the
  source of truth after a change.

## Manage-users UI

- Opening **Manage users** requests a fresh `GET /api/users` snapshot before
  showing the rows, replacing any stale list previously held by the app shell.
- While loading, show the existing dialog shell and a non-interactive loading
  state; do not display a guessed total.
- On a load failure, keep the dialog open, show the existing safe inline error
  treatment, and offer **Retry**. Existing user-management actions remain
  unavailable until a successful list response is available.
- Each user card shows the summary below its username/state line. Format bytes
  using the existing decimal display convention (`B`, `KB`, `MB`, `GB`), with up
  to two fractional digits for GB values; never use scientific notation.
- The summary is text, not a progress bar, warning, sortable control, quota
  editor, or billing signal. No color changes are based on usage.
- Refresh the summary after an action that can affect the visible set or stored
  media lifecycle: archive, restore, delete library, and returning to the modal.
  Editing a username/limit and resetting a password may retain the current
  snapshot until the normal refresh, since neither changes bytes.

## Authorization and privacy

- Only the existing `requireAdmin` route may return cross-user totals.
- Do not add totals to `/api/auth/me`, folder pages, public clip pages, public
  embeds, normal-user search, client storage, logs, URLs, or error responses.
- The normal-user interface has no storage summary in this slice.

## Error and consistency behavior

- A database failure while listing users follows the existing generic,
  non-sensitive administrator list error path; it must not return a partial list
  with missing totals.
- The result is a point-in-time snapshot. An upload, purge, or processing job
  may change the value after the response; no locking or live polling is needed.
- Permanent purge changes the total only after the associated ready clip record
  and assets are successfully removed according to existing transactional
  behavior.

## Verification

- Store tests cover zero media, active ready media, trashed ready media, archived
  library media, excluded non-ready states, and no N+1/duplicate aggregation.
- HTTP tests cover admin totals, normal-user route denial, JSON integer type, and
  unchanged existing list fields.
- Component tests cover loading, error/retry, `0 B`, decimal GB formatting, and
  an example row such as `50 MB per stored clip · User · 1.38 GB used`.
- Existing archive, restore, trash, and purge regressions continue to pass.
