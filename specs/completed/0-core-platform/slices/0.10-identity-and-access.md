# Slice 0.10: Identity and access

## Status

Accepted for version one, subject to the documented browser-session limitation.

## Goals

- Support multiple named users with password-based login.
- Provide exactly one installation owner, called the super-admin.
- Let the super-admin create users and set their restrictions.
- Prevent normal users from reading or changing another user's library.

## Proposed roles

| Capability | Normal user | Super-admin |
| --- | --- | --- |
| Log in and log out | Yes | Yes |
| Browse own library | Yes | Yes, through top-level user roots |
| Browse another user's library | No | Yes |
| Create folders/upload/edit own clips | Yes | Yes |
| Operate on another user's content | No | Yes |
| Create/configure users | No | Yes |
| Create another super-admin | No | No |

The super-admin is a role, not a filesystem folder. Its explorer begins at a
virtual top level containing all account roots. Uploads default to the personal
admin root, while the super-admin may choose any accessible destination.

## Proposed authentication behavior

- Store normalized unique usernames and one-way password hashes, never plaintext
  or reversibly encrypted passwords.
- Authenticate once and issue a random, expiring session in an `HttpOnly`,
  `Secure`, `SameSite` cookie.
- Protect state-changing requests against cross-site request forgery.
- Do not apply an application-level failed-login cooldown or attempt limit.
  Failed responses still avoid revealing whether a username exists.
- Bootstrap the one super-admin through the accepted one-time setup flow; do not
  ship a default credential.
- Record ownership and authorize every library operation on the server. Hiding
  another user's files in the frontend is not an access-control mechanism.

## User management proposal

The super-admin can create a user with:

- Username.
- Admin-chosen password, with no forced change on first login.
- Per-file stored-output size limit.
- Account status: active or disabled.

The stored-file limit is required, uses decimal MB, defaults to 50 MB, and accepts
values from 1 through 500 MB. It applies to that user's uploads; accepted
super-admin operations may bypass it.

Changing restrictions applies to new uploads. Existing clips are not silently
deleted or recompressed unless a later feature explicitly requests that action.

The super-admin may set a new password for any user but cannot view the current
password. One-way hashing intentionally makes the original unrecoverable. A UI
may show a newly entered password while setting it, but must not store or later
reveal it. This remains worthwhile for a friends-only service: database backups,
logs, browser sessions, and reused passwords can escape the intended group.

Normal users cannot change their own passwords. They ask the super-admin, who
sets a replacement. The super-admin may disable or delete a user account. Account
deletion removes login access and archives the identity, but retains its library
under admin control until the super-admin performs a separate library-deletion
action. This separation prevents an account-management mistake from immediately
deleting media.

## Historical extension record: self-service password change

**Status: completed in [`0.17-self-service-password-change.md`](0.17-self-service-password-change.md).** This replaces the
version-one restriction that normal users must ask the super-admin for an ordinary
password change. It is not account recovery: a user who has forgotten the current
password still needs the super-admin to set a replacement.

### User flow

1. The authenticated account menu exposes **Change password** for every active
   normal user and the super-admin.
2. A styled in-app modal requests Current password, New password, and Confirm new
   password. Password fields use the appropriate browser autocomplete hints and
   never prefill or reveal a stored password.
3. The server verifies the current password, validates the existing 8–128
   character password rules, confirms the two new values match, then atomically
   replaces the Argon2id hash.
4. Success shows a concise confirmation with no password value. The modal clears
   all fields before it closes. Failure keeps only non-secret validation state;
   fields are never written to URLs, logs, analytics, or error records.

### API and authorization

- `POST /api/me/password` accepts `currentPassword`, `newPassword`, and
  `confirmPassword`; it requires an authenticated active user, same-origin/CSRF
  protection, and the existing secure session cookie.
- The endpoint always changes only the authenticated account. Client-supplied user
  IDs are neither accepted nor inferred.
- Return `400` for malformed/mismatched new password values and `403` with the
  safe code `current_password_incorrect` when current-password verification fails.
  Return no password-derived detail.
- Reuse the existing Argon2id parameters and secret-safe structured logging rules.
  Log only a safe event such as `password_changed` with account/actor IDs.
- The existing administrator reset-password flow remains available for recovery
  and does not require the old password.

### Accepted session behavior

Changing a password does not revoke or rotate existing signed sessions. The
current session and any other issued session remain valid until their ordinary
24-hour absolute expiry, matching the existing administrator-reset behavior.
The action updates only the password hash and does not require a session-schema
change.

### Acceptance criteria after decision

- [ ] An active normal user and super-admin can change only their own password
      after correctly supplying the current password.
- [ ] A forgotten password still requires administrator recovery; no email,
      token, or self-service reset route is added.
- [ ] Invalid current passwords, mismatched confirmation, and invalid new values
      expose useful safe feedback without changing the hash.
- [ ] Passwords and session values never appear in URLs, logs, API responses, or
      client persistence.
- [ ] Existing sessions remain valid through their ordinary expiry after both
      self-service and administrator password changes.
- [ ] The shared modal supports Escape, X, and accepted backdrop dismissal without
      accidentally submitting the password form.

Account lifecycle semantics:

- **Disable:** blocks login and rejects authenticated use immediately, even when a
  browser still holds a signed cookie. Library and public clip URLs continue working.
- **Archive/delete account:** removes normal login/account visibility and moves
  its retained library to an admin-only archived-users area. Public clip URLs
  continue working.
- **Delete archived library:** uses the folder checkbox/confirmation flow, moves
  the whole library into admin-only trash, and immediately disables its public
  URLs. Normal 90-day permanent-retention rules then apply.
- Newly created users are active immediately.
- The super-admin may rename a normal account; usernames remain case-insensitively
  unique and its retained library/public URLs do not change identity.
- Archived usernames remain reserved while the account/library record exists.
- The super-admin may restore an archived account with the same username/library
  after assigning a new password.
- The sole super-admin may change their own username/password but cannot be
  disabled, archived, deleted, or demoted.
- Five users is expected operational scale, not a hard-coded account limit.

## Initial super-admin setup

- When no account exists, a one-time setup page accepts a long random setup token
  supplied through Docker/Komodo secret configuration.
- The page creates the one super-admin with a chosen username and password hash.
- After successful creation, the setup route permanently refuses further setup,
  even if the setup token remains configured.
- Deployment documentation instructs the owner to remove the token afterward.

## Username and password rules

- Usernames are unique and matched case-insensitively while preserving display
  capitalization; accepted length is 3–32 characters.
- Usernames contain only ASCII letters, digits, `_`, and `-`, with no spaces.
- Passwords are case-sensitive, 8–128 characters, and stored using Argon2id with
  a unique salt.
- Passwords never appear in URLs, logs, audit entries, or API responses.
- Version one stores no email addresses and has no invitations, email recovery,
  or self-service password reset.

## Session behavior

- Login issues a signed cookie containing the internal user ID and issued-at time.
  It is authenticated with an application secret so clients cannot alter it.
- The cookie is `HttpOnly`, `Secure`, and `SameSite=Lax`, with no persistent expiry
  or `Max-Age`.
- There is no remember-me option and no long-lived application session.
- Cookies are shared by tabs. A web application cannot reliably terminate a
  cookie when only one tab/window closes. The browser normally discards a session
  cookie when its browser session ends, although session restoration may retain it.
- Explicit logout immediately clears the session cookie.
- The signed session has a 24-hour absolute validity limit. An open or restored
  browser must log in again after that point.
- Password reset does not proactively invalidate other already-open sessions.
- Disable/archive authorization is checked on every request, so those account
  states block access even if an old browser still holds a session cookie.
- There is no session database table. Every request loads current account state
  from SQLite, so disable/archive takes effect immediately.

## Accepted scope notes

- Version one has no total-storage quota; only per-file stored limits apply.
- The super-admin may transfer an archived library or its folders into another
  active account. Cross-owner move/copy details are specified with library rules.
- The user-management grid contains username, state, stored-file limit, and only
  Edit, Reset password, Disable/Enable, Archive, Restore, Delete library (for an
  archived account), and Open library actions.
- Active and disabled libraries remain in the main admin library chooser. Archived
  accounts are removed from that chooser and appear in the admin-only user manager,
  where the retained library can still be opened.
- Disable requires one confirmation. Archive requires an acknowledgement checkbox
  plus a confirmation button.
- Delete library is available only for an archived normal account. It requires an
  acknowledgement checkbox and moves its complete root subtree into the admin-only
  recycle bin. Public URLs stop resolving in that same database transaction. An
  administrator may restore the root from recycle bin before restoring the account.
  Permanently purging that root after the 90-day retention period deletes the now
  library-less archived account record as the final account-deletion step.
- Version one has no audit-log UI or database audit-event subsystem. Important
  authentication and admin actions are emitted as structured logs without secrets.
