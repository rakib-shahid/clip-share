# Slice 0.14: Modern, simple user interface

## Status

Accepted for version one.

## Experience goals

- Modern and visually polished without feeling like a dense enterprise dashboard.
- Fast and understandable for upload, organization, viewing, and sharing.
- Fully usable on phone and desktop, with accessible keyboard/focus behavior.
- Consistent states for loading, empty folders, validation, transfer progress,
  processing, success, and recoverable failure.
- Dark-only visual theme.
- Grid-based folder and clip explorer; no list-view requirement for version one.
- Display dates/times in the browser's local timezone while API/storage remains UTC.

## Visual direction

- Near-black charcoal page background with slightly lighter elevated surfaces.
- Sky blue is the primary accent.
- Soft borders and restrained shadows establish hierarchy.
- Corners are rounded without making every control pill-shaped.
- Clip cards use compact 16:9 thumbnails.
- Ready clip thumbnails in both the main gallery and recycle bin reveal the same
  centered play affordance on hover or keyboard focus. Activating it opens the
  shared in-app video preview dialog without navigating away.
- Use fast system sans-serif typography.
- Motion is minimal and respects reduced-motion preferences.
- Decorative gradients are avoided except for a rare, purposeful accent.

## Proposed surfaces

### Logged out

- Focused login screen with username and password.
- No disclosure of usernames, library contents, or administrative routes.
- A valid public clip URL is the sole anonymous content surface. Its page contains
  the title, player, and a Home action returning to this login screen, with no
  library or management navigation.
- Direct unauthenticated navigation to `/app/*` goes to login. Direct authenticated
  navigation and browser refresh serve the React route correctly.

### User library

- App shell with breadcrumbs, current folder, search affordance, account menu,
  upload action, and responsive file explorer.
- Folders and clips appear as a responsive grid of cards.
- Clip cards show thumbnail, title, processing/error status, relevant media facts,
  and a quick copy-link action.
- Drag/drop upload on desktop plus an ordinary accessible file picker everywhere.
- Rename uses a clear dialog or intentional inline edit. Move and admin Copy use
  explicit dialogs on every device; drag-to-move is not part of version one.

### Super-admin

- The same explorer begins with user-root cards rather than an admin-owned folder.
- A separate user-management surface creates users and edits limits/status.
- Admin context is visually unmistakable when browsing another user's library.

### Share page

- Video is the visual focus, with title and restrained sharing controls.
- Server-rendered metadata works independently of client JavaScript.
- The public surface contains only title, poster/player, native controls, and a
  context-aware Home action. It has no autoplay, loop, download action, uploader,
  folder, dates, size, related clips, or management controls.

## Design-system requirements

- Define color, typography, spacing, radii, elevation, motion, and focus tokens.
- Meet WCAG-oriented contrast and interaction practices; do not encode status by
  color alone.
- Respect reduced-motion preferences and touch target sizes.
- Use icons with accessible names/tooltips where their meaning is not universal.
- Prefer a cohesive custom theme over a collection of unrelated component demos.
- Build with the accepted React + Vite + TypeScript + Tailwind CSS + shadcn/ui
  stack.
- Repeated interaction patterns use shared components. In particular, upload and
  move flows share one folder browser, clip surfaces share one preview player,
  and folder/clip cards share one Rename/Move/Delete action bar.
- Every modal traps Tab/Shift+Tab focus, restores the previously focused element
  when it closes, and lets Escape close only the frontmost modal. This includes
  nested confirmation dialogs.

## Historical extension record: backdrop dismissal

**Status: completed in [`0.16-shared-dialog-backdrop-dismissal.md`](0.16-shared-dialog-backdrop-dismissal.md).**

Every in-app `Modal`—including Rename, Move, Delete, Upload, Recycle Bin,
previews, folder pickers, user-management dialogs, and nested confirmations—will
close when the user clicks/taps the blurred backdrop outside the card. This is a
dismissal action only: it never confirms, deletes, uploads, purges, or otherwise
submits an action.

- The backdrop closes only the frontmost modal. A click inside the modal card,
  including its empty space, does not close it.
- Backdrop dismissal invokes the same `onClose` path as Escape and the visible X,
  preserving focus restoration and any existing unsaved-change/cancel confirmation.
- A nested confirmation remains open when its parent backdrop is clicked; only
  the nested dialog's own backdrop can dismiss that confirmation.
- Pointer-down/up must both originate on the backdrop before closing. Dragging
  from the dialog onto the backdrop, or from the backdrop into the dialog, does
  not close it.
- The backdrop remains visually non-interactive to screen readers because the
  dialog is modal; keyboard dismissal continues to use Escape and the X button.
- Tests cover ordinary, nested, destructive, upload, and recycle-bin dialogs;
  they assert the close callback fires exactly once and no destructive handler is
  called.

## Completed acceptance criteria

- [x] Primary flows use responsive narrow-mobile and desktop layouts.
- [x] All primary actions are keyboard reachable with visible focus.
- [x] Upload transfer and processing are distinct and understandable.
- [x] Every collection has loading, empty, and error presentation.
- [x] Destructive actions require deliberate confirmation or provide safe undo.
- [x] The super-admin can tell which user's library is currently open.
- [x] The interface passes agreed automated accessibility checks and a manual
      keyboard review.

## Semantic action buttons

Shared action buttons are transparent at rest and use consistent semantic border
and icon colors across authentication, libraries, dialogs, uploads, and the
editor. Hovering applies only a very light translucent tint in the same color.
Semantic buttons must remain visually distinct from disabled controls:
green means a positive/save/upload/finalize action; red means destructive,
discard, delete, disable, or cancel; amber means a warning or deliberate risky
override; blue means a normal creative action such as trimming or rendering;
and neutral outlined buttons mean back, navigation, or secondary actions.
Icon-only controls retain accessible names. Compact editor controls such as
**Set In**, **Set Out**, and **Reset trim** remain visibly button-shaped rather
than relying on hover-only highlighting.

## Design input during implementation

Reference screenshots may refine composition during mockup review, but must remain
within the accepted dark, restrained, sky-blue-accented direction unless this spec
is deliberately revised.
