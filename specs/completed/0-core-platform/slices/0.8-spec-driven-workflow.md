# Slice 0.8: Spec-driven development workflow

## Why

The specifications are the shared source of truth for what the product should do
and why. Code demonstrates the current implementation; specs preserve intent,
tradeoffs, edge cases, and acceptance criteria.

## Status vocabulary

- **Draft:** incomplete exploration; implementation must not depend on it.
- **Proposed:** ready for review, with material open questions visible.
- **Accepted:** agreed scope and behavior; implementation may begin.
- **Implemented:** accepted behavior exists and its required checks pass.
- **Superseded:** replaced by a linked newer decision or spec.

## Lifecycle

1. **Explore:** discuss the problem, user, constraints, examples, and alternatives.
2. **Specify:** write goals, non-goals, behavior, states, data/API impact, security,
   operations, acceptance criteria, and tests.
3. **Review:** resolve material questions and mark the spec Accepted.
4. **Plan a slice:** choose the smallest end-to-end set of acceptance criteria.
5. **Implement:** write readable code and tests. Avoid unrelated refactors.
6. **Verify:** run focused tests, the broader suite, and relevant Compose/browser
   checks. Record limitations rather than silently narrowing the spec.
7. **Reconcile:** update docs for intentional changes and mark Implemented only
   when all acceptance criteria are satisfied.

## Definition of ready

A feature is ready for implementation when:

- Its user and problem are clear.
- Goals and non-goals bound the work.
- Permissions, important failures, and UI states are described.
- API/data/storage and deployment impacts are understood.
- Security and privacy implications have been considered.
- Acceptance criteria are testable.
- No open question could materially change the implementation.

## Definition of done

- Accepted criteria are implemented without known silent deviations.
- Code is formatted and relevant automated tests pass.
- The Docker development path works for the changed behavior.
- Errors and logs are useful without leaking credentials or private data.
- New configuration is documented with safe examples.
- Non-obvious implementation choices are documented where they matter.
- The spec status and related README links are current.

## Decision discipline

Small reversible implementation details can be selected during coding and noted
in the handoff. Choices that alter product behavior, security, persisted data,
deployment topology, or the technology stack require an explicit spec decision.

Architecture decisions that affect multiple features should use a short record:

```markdown
# ADR-NNN: Decision title

## Status
Proposed | Accepted | Superseded

## Context
What forces the choice.

## Decision
What we chose.

## Consequences
Benefits, costs, and follow-up work.

## Alternatives considered
Other viable choices and why they were not selected.
```

## Suggested first sequence

1. Review `features.md` and agree on the version-one Must features.
2. Decide `frontend-framework.md` and record the result.
3. Specify authentication and clip visibility semantics.
4. Specify the upload/processing lifecycle and limits.
5. Accept an initial architecture and Docker topology.
6. Scaffold only what those accepted specs require.
7. Build a vertical slice: health check, one upload, processing, persisted
   metadata, share page, and restart verification.
