# Slice 0.11: User libraries and folders

## Status

Accepted for version one.

## Core model

Every account, including the super-admin, owns one library root. Within that
root, the owner may create nested folders and upload, view, edit, move, and
delete clips. The super-admin starts at a virtual installation root whose
children are all account roots, including a personal admin root. Uploads default
to the personal admin root, but the super-admin may choose any folder they can
access.

```text
super-admin view
├── admin (personal, default upload destination)
├── alice
│   ├── game-clips
│   └── misc
└── bob
    └── tournaments

alice view
├── game-clips
└── misc
```

## Important design decision

Folders should be logical database records, not user-controlled physical paths.
Clips should have opaque immutable IDs and server-generated storage paths. A
rename or move then updates SQLite metadata without moving a large video on disk,
and the public share URL remains stable.

This also prevents `../` traversal, OS-specific filename trouble, collisions,
and broken Discord links. The UI may look and behave like a filesystem while the
storage layer remains safe and simple.

Proposed records:

- A folder has an ID, owner user ID, optional parent folder ID, and display name.
- A clip has an ID, owner user ID, folder ID, display title, processing state,
  visibility, and references to server-owned media assets.
- Every clip has exactly one immediate parent folder. That parent may be nested
  within other folders up to the accepted depth limit. A move replaces the parent
  relationship; it does not create a second reference or copy the media.
- Folder display names and clip display titles are unique within their immediate
  parent folder, compared case-insensitively. A different folder may reuse the
  same name/title.
- Display names are metadata only. Renaming a clip never changes its opaque public
  ID or server-owned physical filename.
- Rename and move both explicitly check the active sibling-title invariant before
  writing. This gives callers a clear conflict result even if a database driver
  cannot expose a partial-index constraint consistently.

## Names and hierarchy

- Usernames contain 3–32 characters and are unique case-insensitively.
- Folder names contain 1–100 characters.
- Clip display titles contain 1–200 characters.
- Folder nesting is limited to 20 levels below an account root.
- Names cannot be blank, equal `.` or `..`, contain control characters, or end in
  whitespace.
- Folder names and clip titles may contain Unicode and internal spaces. Normalize
  Unicode for comparison, trim leading/trailing whitespace, and reject `/` and
  `\` in addition to control characters and reserved dot names.
- Folder names and clip titles each have their own namespace. A folder and clip
  may share a display name because their types are visually distinct.
- A conflicting create, rename, move, or restore is rejected or resolved through
  the explicit restore-conflict rule; existing content is never overwritten.
- Account library roots cannot be renamed, moved, trashed, or deleted through
  ordinary folder operations. Renaming an account changes its displayed root
  label; deleting a library uses the separate admin lifecycle.

## User flows

1. A user opens their library and sees folders and clips in the current folder.
2. They create and enter nested folders using breadcrumbs.
3. They upload into the current folder or choose another destination.
4. They edit a clip title or move it to another folder they own.
   The move dialog uses the same folder browser as folder moves and never asks
   the user to enter an internal numeric folder ID.
5. The super-admin enters a user's root and can perform the allowed admin actions.
6. Deleting a clip opens a warning with one additional explicit Delete/Confirm
   button after the initial delete action.
7. Deleting a folder requires both acknowledging a warning checkbox and then
   pressing the enabled Delete/Confirm button.
8. Authenticated users can search their accessible library by clip title or folder
   name. The super-admin's search may span every active/archived library.

## Version-one explorer behavior

- Upload handles one video at a time; batch upload is deferred.
- Within a folder, folders appear first in case-insensitive alphabetical order,
  followed by clips ordered newest upload first. Sorting is not customizable.
- Folder pages return at most 60 items initially and use an explicit **Load more**
  action rather than infinite scrolling.
- Search is case-insensitive and recursive across folder names and clip titles.
  Normal users search only their library; super-admin search covers active and
  archived libraries. Results are capped at 100 with no advanced filters.
- Search uses substring matching. An empty query returns no search results, active
  search excludes trash, and trash is browsed through its dedicated screen.
- Search is available from the authenticated app shell, so it works from both the
  admin library chooser and any open folder. Results use compact cards showing the
  matching type and logical path. Opening a folder result enters that folder;
  opening a clip result enters its containing folder. Ready clip results may also
  be previewed or have their public link copied without leaving search.
- Clip editing supports display-title changes and moves only. Replacing underlying
  media requires uploading a new clip.
- Folder copy is all-or-nothing. Any case-insensitive destination name conflict
  rejects the whole copy and reports every conflict; nothing is auto-renamed.
- Copy places a new folder with the source folder's name inside the chosen
  destination. Because the subtree receives entirely new parent folders, only
  collisions at that destination level can conflict; the response still uses a
  conflict list for a stable UI contract. Copy cannot use an account root as its
  source or place a copy inside its own source subtree.
- Version-one folder copy is a synchronous administrator action. It rejects a
  subtree containing uploading/processing clips and can be retried after they are
  ready. The UI shows a busy state until the complete operation commits.
- Concurrent conflicting mutations are serialized by SQLite: the first committed
  operation wins and later conflicts return a clear error without overwriting.
- Normal users move content only within their own root; cross-user move/copy is
  exclusively a super-admin operation.

## Super-admin authority

The super-admin has full control over every active and archived library: browse,
search, upload, create, rename, move, trash, restore, and permanently purge. Each
important admin mutation is emitted as a structured application log without
passwords, session tokens, or private media contents. Version one has no audit-log
screen or database audit subsystem.
The super-admin may also move or copy complete folder subtrees between account
roots.

- A move preserves folder/clip identities, physical media, and public URLs while
  recursively changing ownership and parentage.
- A copy creates independent folders and clips with new IDs, new public URLs, and
  duplicated physical MP4/poster assets. Copied content can be renamed, moved,
  trashed, restored, or purged without affecting its source.
- Copy bypasses the destination owner's stored-file limit because it is a
  super-admin action. It still validates names and commits all-or-nothing so a
  partial copied tree is never exposed after failure.

## Trash and retention

Deletion is a recoverable state change, not an immediate physical erase:

- Deleting a clip moves that clip into trash.
- Deleting a folder moves the entire folder subtree, including all nested folders
  and clips, into trash as one recoverable unit.
- The warning for a folder shows its recursive item count and total stored size.
- The folder-deletion dialog loads that summary when opened. Its acknowledgement
  checkbox and confirmation action remain disabled until the summary loads; a
  failed request is shown inline and can be retried without closing the dialog.
  The folder count includes the selected folder itself.
- The deleting user can browse and restore their own trashed content for 30 days.
- After day 30, normal users can no longer see or restore it, but the super-admin
  can review or restore it through day 90.
- After 90 days, a background retention job permanently removes database records
  and stored media. Retention age is measured from the original deletion time and
  does not reset merely because the item becomes admin-only.
- Restoring a folder restores its subtree. If its original parent no longer
  exists, it is restored to the owner's library root; naming conflicts must be
  handled without overwriting existing content.
- Trashing immediately makes affected public clip pages/media unavailable.
  Restoring reactivates the same immutable public URLs.
- Trashed content is read-only except for restore or purge.
- Authenticated owners may preview an individually trashed clip during their
  30-day visibility window. The super-admin may preview it through day 90.
  Preview uses an authenticated trash-media route; the public URL remains disabled.
- If restoration conflicts with an existing folder name, append ` (restored)`,
  adding a number if required. If an individual clip title conflicts, apply the
  same suffix rule.
- Restoring clears the deletion timestamp. A later deletion begins a fresh
  retention period.
- The super-admin may purge before day 90 using the stronger checkbox plus
  confirmation flow; early purge is irreversible.

## Completed acceptance criteria

- [x] A normal user's explorer root never reveals other usernames or libraries.
- [x] Users can create nested folders with validated display names.
- [x] Users can browse their own folders and existing clips with breadcrumbs.
- [x] Users can change a clip title and move it within their own library.
- [x] A move or rename does not change the clip's share URL.
- [x] The super-admin sees user roots at the top level, not an `admin` folder.
- [x] The super-admin's personal root appears alongside other account roots and
      is the default destination for admin uploads.
- [x] Server authorization rejects cross-user IDs even when manually submitted.
- [x] Clip deletion requires one confirmation step after the delete action.
- [x] Folder deletion requires a warning checkbox and a separate confirmation
      button; the button remains disabled until the checkbox is checked.
- [x] Deleting a folder trashes its complete subtree as one restorable unit.
- [x] Owners can browse and restore their trash through 30 days after deletion.
- [x] Days 31–90 are visible/restorable only to the super-admin.
- [x] Content older than 90 days is permanently removed by a retry-safe background
      retention job.
- [x] Folder-deletion warnings show recursive item count and stored size.
- [x] Folder names and clip titles are case-insensitively unique within their
      immediate folder and obey accepted length/character limits.
- [x] Unicode comparison normalization and prohibited path/control characters are
      enforced without changing the displayed value beyond outer trimming.
- [x] Renaming a clip changes only display metadata, never physical names or URLs.
- [x] Users can search accessible folders and clip titles; no bulk actions exist
      in version one.
- [x] Folder pages sort folders alphabetically before newest-first clips, return
      60 items initially, and load more only on request.
- [x] Search follows the accepted scope and returns no more than 100 results.
- [x] Empty search returns no matches, active search excludes trash, and search
      cannot cross authorization boundaries.
- [x] Clip editing cannot replace underlying media.
- [x] Any Copy name conflict rejects the entire operation and lists conflicts.
- [x] The super-admin has full control over active/archived libraries and admin
      mutations produce secret-free structured logs.
- [x] Trash immediately disables public media; restore reactivates the same URL.
- [x] Cross-owner folder moves retain public URLs and recursively change ownership.
- [x] Account roots reject ordinary rename/move/delete and concurrent conflicts
      never overwrite existing content.
- [x] Folder copies create independent media and new public URLs, and failure does
      not expose a partially copied subtree.

## Deferred beyond version one

- Tags, favorites, collections, aliases, or shortcuts that could surface one clip
  in more than one organizational view.
- Bulk move/delete operations.
